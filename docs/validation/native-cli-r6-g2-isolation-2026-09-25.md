# R6-G2：历史压力、原生 CLI 与多 Run 隔离（2026-09-25）

本记录补充 [G1 规模验证](native-cli-r6-g-scale-2026-09-24.md) 的功能隔离证据，以原 P07 测点对照延迟。实施状态统一在 [实施计划](../v2-implementation-plan.md#r6-g规模故障和用户试用交付) 维护。

## 1. 环境与范围

- Apple M3 Max / 36 GiB，macOS 26.5.2，debug 构建，系统 Chrome 153.0.8010.53（headless），安装版官方 CLI 0.156.1。
- 基线提交 `466dff7` 加工作区 G1/G2 改动；性能矩阵串行运行，计时期间不并行编译或运行其他测试。每组独立临时 HOME/USERPROFILE/CODEX_HOME、临时历史与派生缓存，不使用真实会话、凭证或模型服务。
- 复用 `examples/r0-latency.rs` 和 `examples/r0-native-latency.rs` 的原测点，测量体共用 `examples/support/r0_web_timing.rs` 与 `r0_native_timing.rs`，通过测试专用入口在计时前启动同进程 HistoryLibrary；未将模型首字或 PTY 渲染延迟当作代理内部附加延迟。
- Web 组使用正式工作台资源、真实 Chrome、`/bin/cat` PTY 和 Recorder，但不含官方 CLI；原生组使用安装版 CLI、合成 SSE 和原生 rollout 完成记录，不含浏览器/工作台 Recorder。两组互补，不能宣称一次实验覆盖了所有组件。本轮压力延迟覆盖 HTTP/SSE；WS 转发保留已有功能回归，不新增 WS 压力时延承诺。

## 2. 压力必须实际生效

| 负载 | 施加方式与断言 |
| --- | --- |
| idle | 无全局历史工作线程，作为同机参考 |
| index | G1 相同的 10,000 会话 / 200,000 item / 2,306,150,000 实际字节合成来源；默认 512 MiB 预算，每组新派生库。开始时已进入 indexing 且有进度，结束时仍 indexing、进度增加 |
| legacy-lock | 合成 schema 25 旧库完成初始读取后持有 `BEGIN EXCLUSIVE`；每 25ms 请求刷新，测试钩子记录实际 reader 打开失败，要求测量生命周期内至少 2 次 `source_busy`；退出后源库字节不变 |
| query-flood | 派生库持有独占锁，每批 64 个并发目录查询，反复提交；至少 2 批完成且实际出现 `library_busy` 和 `cache_invalid`，禁止悄悄返回成功空列表 |

旧库尝试计数范围从负载激活后到测量函数返回，包含 CLI 退出、Chrome 收尾及 Recorder 追平阶段，不等于精确的网络首末字节窗口。最初开发探针只触发一次锁读，之后线程回到重扫等待；该版本未作为压力验收，最终版本改为持续刷新并记录真实尝试。

查询队列容量为 16，存活线程下实际出现 `sync_channel::Full`，据此推断峰值达到 16；不是新增的生产队列监控计数器。持锁关闭 HistoryLibrary 要求小于 2 秒。活动 SQL 的调用取消、独立索引线程 CPU 和自然业务峰值仍不能从本实验推出。

## 3. Web 转发、页面与保存

完整矩阵 12 组通过，耗时 182.06s（含生成来源）。短输出每组 400 个标记、长输出 400 个、四路并发共 800 个；各组客户端、观察器、DOM 与 Paint 时间样本齐全，共 6,400 个。观察丢块、流中断、页面异常均为 0。短/长组 Recorder 持久水位 404/404，并发组 816/816，历史覆盖均为 `complete_for_observed_scope`。

Rust 进程生命期 RSS 峰值 69,304,320B（约 66.09 MiB），包含夹具、代理、观察器、网页服务、Recorder、测量及同进程历史线程，不是单个组件指标。计时区间 Rust CPU：idle 0.477–0.803s，index 4.479–5.227s，legacy-lock 0.618–0.916s，query-flood 0.520–0.769s，说明索引负载实际消耗 CPU。Chrome 进程组采样 RSS 最大 1,615,072 KiB（约 1577.2 MiB），JS 堆最大 19,253,136B（约 18.36 MiB），每组 CPU 2.011–5.193s；包含 Chrome/trace 等开销，不能当作产品页面净内存或任意时刻的精确峰值。

## 5. 多 Run 容量与输入隔离

新增 `concurrent_capacity_rejection_preserves_input_and_stop_isolation_without_replay`：先启动 3 个 Run，再让 4 个请求争用第 4 个名额。启动队列忙时明确返回 HTTP 503 `launch_busy`，显式重试后超容量操作明确失败为 `run_capacity`。统计脚本真实调用次数，确认被拒请求没有额外探测或启动 CLI。

4 个 Run 分别持有自己的终端输入权，各自 PTY 子进程只消费本项目输入。停止其中一个后，它拒绝后续输入，其余 3 个继续消费自己的第二条输入。再次提交旧失败 operation 仍失败，不因空出名额自动重放；新 operation 才能使用释放的名额，且不继承旧输入。Application 保持健康。

该测试使用合成 shell CLI、真实 PTY、HTTP 启动/停止 API 和内部 TerminalHandle；不是官方 CLI 四开或终端 WebSocket 端到端压力实验。沿用先前多 Run 的浏览器/WS 验证范围，不用此项替代。
