# R6-G1：索引线程 CPU、正文吞吐与缓存边界（2026-09-30）

本轮补齐 [G1 规模基线](native-cli-r6-g-scale-2026-09-24.md)未单独测量的工作线程 CPU 与纯正文处理成本。阶段状态只在[实施计划](../v2-implementation-plan.md#r6-g规模故障和用户试用交付)维护；本记录不代替 G4 整片交付或用户试用。

## 1. 环境与测量方法

- 基线 `d9a577b`，分支 `codex/r6-g1-resource-validation`；仅增加测试和文档，生产算法、界面、配置与派生格式不变。
- Apple M3 Max、36 GiB、macOS 26.5.2；Rust 1.95.0、Node 22.23.2。先用标准入口构建 Web/release，再串行运行 release 专项；不把 debug 与 release 的差值归因为本轮代码提速。
- `resource_tests.rs` 在 macOS 测试构建内，对存活的 `history-library-index` / `history-library-query` JoinHandle 调用 Mach `THREAD_BASIC_INFO`，分别读取 user/system CPU。初次发布读新线程生命周期累计值，暖查询与刷新读前后差；不包含生成器、测试线程或另一工作线程，不使用 `ps %cpu` 的历史平均值代替区间消耗。
- 墙钟从启动库前至观察到提交完成，轮询粒度约 20ms；准备、写入及核验样本在计时外。新缓存不等于冷磁盘：源文件刚写入，未清除 OS 页缓存。
- RSS 是 `getrusage(RUSAGE_SELF)` 的整个测试进程生命周期峰值，包含生成/核验及之前样本，不是线程内存，也不冒充单样本瞬时峰值。
- 所有来源均为 TempDir 中的合成 JSONL/派生库，未启动 CLI、浏览器或真实模型，未读取私人正文。新建派生目录不删除原始历史。没有后台调试服务留存。

## 3. 四类纯正文矩阵

中文、英文、代码/Markdown/Unicode、含合成 bearer 凭证，各运行三个独立新缓存样本。每组 32 会话、640 条消息，目标单条长度为 512B / 4KiB / 16KiB / 24KiB，重复完整片段，实际字节由 manifest 记录；没有图片或 Base64 省略来虚增吞吐。

每个样本完整保留 672 条记录（含 32 条 session metadata），计时结束后逐条对照全部 640 条 raw 正文，检查唯一性及详情未省略。凭证预期独立替换已知合成 bearer 字面量，不调用生产 sanitizer 生成期望值；同时检查凭证没有进入记录。只允许搜索摘录导致的 `search_excerpt_limit` / `entry_coverage_partial`，拒绝正文缓存、详情等缺口。

| 语料 | 输入正文 MiB | 发布墙钟中位数（范围） | 索引 CPU 中位数 | 输入正文吞吐中位数 |
| --- | --- | --- | --- | --- |
| 中文 | 7.014 | 0.153s（0.152–0.155） | 0.122s | 45.80 MiB/s |
| 英文 | 6.992 | 0.852s（0.852–0.853） | 0.825s | 8.21 MiB/s |
| 代码/Markdown/Unicode | 6.993 | 0.636s（0.635–0.636） | 0.608s | 11.00 MiB/s |
| 合成凭证混合文字 | 7.013 | 0.562s（0.549–0.569） | 0.529s | 12.48 MiB/s |

矩阵各次发布采样中最大的进程生命周期峰值 RSS 为 24.5 MiB。吞吐包括解析、脱敏、写缓存、提交及观察到完成；不是单个脱敏函数速度。中文/英文的成本仍不同，没有预设“纯正文必须达到某吞吐”的既定门槛，也不从 12 个固定样本推广为任意文本性能保证。正文完整与搜索完整分别断言，搜索仍受每会话 64KiB 摘录约束。

## 4. 超过 200 MiB 的纯正文预算压力

另一独立样本包含 1024 会话 / 20,480 条英文消息：源 238,879,744B，正文净字节 234,629,120B（约 223.8 MiB），仍使用默认 512 MiB 配置。

- 发布 11.028s；索引 CPU 10.823s（user 10.020 / system 0.803），查询线程 0.000932s。
- 1024 个原生 ID 全集对账一致；只缓存 1449 条记录，派生目录 37,371,904B，覆盖明确 `cache_budget`，不将省略后的数据量算作完整正文缓存吞吐。
- 抽取一个没有缓存记录的会话，按需窗口读到第 3 条消息标记，源文件内容 hash 前后不变；发布采样时记录的进程生命周期峰值 RSS 20,037,632B。

该组补充正文较大时的索引成本与预算行为，不替代多 GB / 10k 会话组，也不宣称所有正文都进入搜索。

## 5. 缓存补全边界

新增常规回归：同一 32 会话纯中文样本，64 MiB 配置下保留全部会话和 147 条记录；增至 512 MiB 并确认新 generation 已提交后，未变化检查点仍复用 147 条。第 3 条消息标记不出现在标题，搜索确实未命中，按需源窗口仍可读。

使用全新测试派生目录重建后恢复 672 条记录，逐条验证 640 条正文、源字节未变，第 3 条消息标记可命中；每会话搜索摘录仍是 partial。这证明当前文档中的重建边界，不是新增自动补缓存功能，也不是让用户删除原生历史。尚未提供新的网页“重建全部缓存”动作。

## 7. 复现与交付边界

先通过 `node scripts/dev.mjs build --offline --release` 准备构建；诊断日志按[受管产物流程](../development/README.md#构建产物生命周期)登记，再串行执行：

```sh
cargo test --locked --offline --lib g1_fresh_cache_restores_omitted_text_but_budget_increase_alone_does_not -- --nocapture --test-threads=1
cargo test --locked --offline --release --lib g1_pure_text_worker_cpu_and_throughput -- --ignored --nocapture --test-threads=1
cargo test --locked --offline --release --lib g1_scale_10000_sessions_200000_items -- --ignored --nocapture --test-threads=1
cargo test --locked --offline --release --lib g1_pure_text_default_cache_pressure -- --ignored --nocapture --test-threads=1

```

线程 CPU 探针和新增资源模块仅在 macOS 测试构建启用，不据此新增 Linux/Windows 支持承诺。未新增用户配置、migration、产品计数器或运行开销，未替换用户实例。G4 的说明整理、整片验收与用户试用另行推进；本次不会自动推送、合并或发布。
