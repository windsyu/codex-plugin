# V3 实施计划：先接入消息渠道，再设计跨会话管理

> 需求确认日期：2026-10-09。
> 当前状态：P0a/P0b/P0c 隔离探针自动化通过，等待用户查看。P1 的 Service/API/UI 文本闭环已接入本地源码，仍进行中、未验收；P2/P3 和跨会话管理未完成。代码入口可用不等于阶段验收通过。

[文档总索引](README.md) · [V2 实施计划](v2-implementation-plan.md) · [支持范围](codex-native-cli-workbench-support.md) · [开发指南](development/README.md)

## 1. 目标与实施顺序

V3 首先让使用者通过消息渠道与本机指定的已有原生会话交互；随后再独立设计如何通过渠道管理多个会话。渠道接入、跨会话管理是两个不同的需求，不能合并成必须同时完成的大改造。

实施顺序为：

1. **渠道接入**：先以 Telegram 完成单个已有会话的消息输入、回复与必要交互闭环，可独立交付。
2. **跨会话管理**：另行确认用户体验、范围与验收，再设计会话选择、切换及任务归属。

后端调整服务于这两个需求，不作为第三个独立前置项目。第一阶段允许补齐必要的后端能力，但不要求先完成跨会话管理或整体重构。

## 2. 第一阶段：已有会话的 Telegram 渠道接入

### 2.1 已确认范围

- 首个渠道为 Telegram，先覆盖单个绑定使用者及其指定私聊，不扩展到群聊或多用户控制。
- 使用者在本机明确指定一个已经由 gateway 管理的原生会话，为它添加 Telegram 输入与回复渠道；不是接管任意外部 CLI，也不是另建一套默认 IM 专属会话。
- Telegram 消息提交到该会话，沿用该会话的上下文；本机指定目标不等于已经实现 Telegram 端会话管理。
- 仅向 Telegram 回传由 Telegram 发起任务的回复，以及推进这些任务所需的必要交互。审批、追问等交互的具体支持范围、响应方式与降级路径仍须设计和验证，不能宣称已有远程闭环。
- 本机发起的对话不自动转发到 Telegram；渠道不是已有会话全部消息、历史或终端输出的镜像。
- 需求已确认不代表已有发送 API、任务归属、回复路由或交互能力满足要求；须以本项目的实现与验收证据确认。

### 2.2 第一阶段非目标

- Telegram 端会话列表、会话选择或切换、新建会话及历史恢复。
- 多会话调度、跨会话队列、跨会话审批管理或多主体控制内核。
- 一次接入所有消息平台；其他渠道在 Telegram 最小闭环验证后再按需求安排。
- 自动广播本机对话、历史正文、reasoning、完整命令输出、cwd 或 diff。
- 自动开放公网监听、部署远程服务或承诺 Linux/Windows 运行支持。

### 2.3 需要形成的验收证据

以下是后续设计和实现必须证明的用户结果，不是已通过的检查：

1. 本机可以明确指定已有受管会话；绑定使用者通过 Telegram 提交消息后，目标会话收到输入并继续上下文。
2. Telegram 发起任务的回复回到原渠道；本机发起的对话不被自动外发。不能证明来源归属时，不将内容当作已归属的渠道回复。
3. 必要审批、追问及错误能按已确认的支持范围处理，未支持的交互明确告知；不绕过原生权限、不默许审批，也不强制压制追问。
4. 未授权使用者不能提交消息或读取会话内容，凭证与私人正文不进入诊断日志、fixture 或 Git。
5. 渠道失败、慢发送和慢存储不阻塞原生 CLI 转发；未送达、未确认或观察缺口不能伪装为成功。

输入确认、整轮完成、重复消息、断线恢复、会话退出，以及本机与 Telegram 同时输入的规则，须在第一阶段详细设计中明确。PTY 写入 ACK 不等于消息提交已确认，模型 response completed 不等于 Codex Turn completed；不能直接用这些信号宣称任务完成。

## 3. 第二阶段：跨会话管理独立设计

第一阶段闭环后，再确认跨会话管理想达到的用户效果。待讨论事项包括渠道中的会话选择/切换，以及任务、队列和审批如何归属到正确会话。

本阶段尚未确认具体操作、命令、默认会话、调度策略、数据模型或接口，不提前将这些规则写入第一阶段。新建、恢复等能力是否纳入第二阶段，也需单独确认，不能从既有网页能力或历史多主体方案自动推导。

## 4. 后端按需求补齐，不预设实现路线

先明确各阶段的输入、回复、必要交互和失败结果，再逐项核对当前后端能力，选择满足要求的最小变更。必要调整可以发生在第一阶段，不要求第二阶段设计完成才开始；反过来也不能用当前实现限制替代用户需求。

P1 当前选择默认关闭的独占 App Server、原版 remote TUI 与透明原生 relay，具体边界见 ADR 0055；这不是所有 V2 Run 的默认运行方式。实验模式拒绝 named profile，不恢复旧 Session Kernel 作为强制依赖。

V3 实验实现不改写 [ADR 0039](decisions/0039-cc-viewer-style-runtime.md) 的 V2 默认入口契约；其有限扩展由 ADR 0055 记录，并单独验证安全和兼容边界。保留原版官方 CLI，不维护补丁、不自动升级；旧 `/v1` 继续只读。

2026-10-09 的源码核对、用户流程草案、能力缺口与首片验收用例见 [Telegram 渠道开工检查](v3-channel-preparation.md)。该准备记录不锁定技术路线，不改变本计划已确认范围，也不表示渠道功能已实现。

## 6. 源码交接与开发环境

源码交接目标为现有仓库的 `codex/v3-channel-planning` 分支，包含此计划与完整受版本控制的项目源码。推送成功后，服务器获取方式：

```sh
git clone --branch codex/v3-channel-planning https://github.com/windsyu/codex-plugin.git
cd codex-plugin
node scripts/dev.mjs doctor
node scripts/dev.mjs bootstrap
```

开发工具链固定为 Rust 1.95.0（含 rustfmt、Clippy）和 Node 22.23.2，沿用 `node scripts/dev.mjs` 标准入口、锁定依赖及 Cargo `--locked`。构建先 Web 后 Rust；具体命令与产物管理见[开发指南](development/README.md)。

Linux 可获取源码继续编写，但尚未完成运行支持验收。源码可克隆、工具链可准备，不等于 Linux 工作台、CLI 或 Telegram 已受支持；实际受测范围仍以[支持说明](codex-native-cli-workbench-support.md)为准。

源码交接不包含依赖目录、构建产物、数据库、凭证或私人会话，也不自动合并、发布、部署服务器或上传其他分支。V2 原状态及验收证据继续只在 [V2 实施计划](v2-implementation-plan.md)维护，不因 V3 规划而重写。
